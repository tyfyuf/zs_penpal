# 故事拆解规范 · 详细逻辑说明

本文说明把"小说或剧本的纯文本"拆解成"LLM 易读的单文件 Markdown"的完整逻辑、设计取舍与每一步的判定规则。技能本体见 `story-decomposition/`，本文是面向人阅读的说明。

## 1. 要解决什么问题

下游 LLM 处理一篇长文本时会遇到两个真实痛点：

1. **上下文装不下**：一整本书塞不进一次对话，读了后面前面就丢。
2. **信息找不到**：某个人物、某条伏笔、某句台词散落在原文各处，难以精确召回。

因此这个技能不做"把书压缩成摘要"，而是**给原文造一张可跳转的地图**：LLM 先读地图掌握全局，再按锚点精确跳回原文。产物是"索引 + 锚点"，不是对原文的破坏性改写。

## 2. 三条贯穿始终的原则

1. **地图在前，原文在后**：输出文件里，总览、结构图、索引、场景卡排前面，原文摘录排最后。LLM 从上往下读，上下文耗尽时应优先丢原文而不是地图。
2. **两段式分工**：切分用确定性脚本，理解用 LLM。脚本负责可靠的编号与边界，LLM 负责它擅长的语义判断。这样锚点稳定、可复现、可重跑。
3. **保真度随字数分级**：短文本保留全文，长文本逐步降级为纯地图，详见第 4 节。

## 3. 输入与输出

- **输入**：纯文本文件（`.txt`，兼容 `.md`）。
- **编码**：自动检测 UTF-8 / BOM / GBK / GB18030；识别不了则声明"无法识别编码，请转存 UTF-8"并不予处理。
- **输出**：单个 Markdown 文件。
- **拒绝**：空文档（0 字）或超过 15 万字，声明"不予处理"并停止。

## 4. 档位机制（保真度分级）

档位按输入字数判定。字数口径是**去除空白后的字符总数**，中英文标点均按 1 字计，面向中文文本。

| 档位 | 字数 | 原文处理 | 场景卡 | 关键台词 |
|---|---|---|---|---|
| 精读 | ≤ 2 万 | 全文保留 | 标准档 | 保留 |
| 平衡 | 2 万 ~ 5 万 | 关键场景原文 + 关键台词，其余摘要 | 标准档 | 保留 |
| 总览 | 5 万 ~ 15 万 | 基本不留原文，只留锚点 + 极少量金句 | 速览档 | 不保留 |
| 拒绝 | > 15 万 | 声明"超过规定字数，不予处理" | — | — |

为什么分档：单文件 + 无损保留，在长篇下会直接爆掉上下文。分档让同一套流程在短篇下自包含、在长篇下退化为轻量地图。

补充规则：

- < 1000 字：按精读档全文保留。
- 空文档：不予处理。
- 平衡档"关键场景"判定优先级：转折 > 揭示 > 冲突升级 > 含关键台词。

## 5. 坐标系统

坐标系统是整个拆解的骨架，决定了下游能不能可靠地"跳回原文"。

### 5.1 锚点

锚点 = **位置 + 短引文**，用于场景卡、人物卡、伏笔条目回指原文。

- 小说：位置是**段落号**，按原文段落顺序从 1 全局递增编号。
- 剧本：位置是**场号 + 行偏移**，行偏移指该场内从场景标题行起算的第几行。
- 短引文：8~15 字，取自锚点位置，即使不打开原文也能凭上下文定位。

示例：

```text
小说：段 042 · "他推开门，看见…"
剧本：s03 · 行 12 · "不，我不能走。"
```

选择段落号而非行号，是因为换行格式变化时行号容易漂移；短引文则让锚点在行号失效时仍可用。

### 5.2 场景 ID

| 模式 | ID 形式 | 示例 |
|---|---|---|
| 小说（有章） | `s{章}-{章内序}` | `s12-03` |
| 小说（无章） | `s{全局序}` | `s03` |
| 剧本 | `s{场号}` | `s03` |

ID 由确定性切分分配。用"章内序号"而不是全局递增序号，是为了原文局部增删时只影响本章、不让后面所有 ID 漂移。

### 5.3 canonical 名与别名

同一个人物可能有多个称呼（名字、绰号、身份）。拆解时维护 **canonical 名 + 别名表**，场景卡和索引只引用 canonical 名，别名只出现在人物卡的别名列表里。这保证跨场景检索不会因称呼不一而断裂。

## 6. 场景卡 schema

场景是拆解的最小粒度，不做节拍（beat）级拆分。

标准档字段：

```text
id          s12-03
章/幕       第12章 · 第二幕
场景功能    推进 / 揭示 / 转折 / 铺垫 / 收束
冲突       谁 × 谁 × 什么
情绪弧     从 X 到 Y
读者新增信息  读者新知道了什么
人物新增信息  人物新知道了什么
出场       人物 · 地点 · 故事内时间
因果       前因(s12-02) → 后果(s12-04)
关键台词    1~3 句（仅精读/平衡档）
锚点       位置 + 短引文
```

字段设计说明：

- **场景功能 / 冲突 / 情绪弧**：回答"这个场景在叙事上干什么、张力在哪、情绪往哪走"。
- **读者新增信息 / 人物新增信息**：刻意拆成两项，因为戏剧反讽正是"读者知道、人物不知道"；合并成一项会丢掉这层信息。
- **出场**：人物统一用 canonical 名；地点和故事内时间用于定位。
- **因果**：连接前后场景，形成情节链；章首/章尾允许一侧为空并标注 `无`。
- **关键台词**：只在保真度高的档位保留，是平衡档"关键场景原文"的落点。
- **锚点**：把场景卡和原文焊在一起。

速览档只保留 `id / 章幕 / 场景功能 / 冲突 / 读者新增信息` 五项。

字数硬上限：

- 速览档场景卡 ≤ 100 字。
- 标准档场景卡 ≤ 200 字（不含关键台词与锚点）。
- 总览档"地图部分"（总览至场景卡，不含原文摘录）≤ 3 万字；超出时优先压缩场景卡，不删索引。

## 7. 全书级索引

- **人物卡**：canonical 名 + 别名 + 出场章节 + 关系（可选：身份 / 目标 / 弧线）。
- **伏笔表**：埋点锚点 + 回收锚点 + 状态（已回收 / 未回收）。伏笔靠 LLM 判断，低置信度条目标注"待确认"。
- **地点 / 物件**：名称 + 别名 + 出场章节 + 简述。

伏笔表用两端锚点（埋在哪、回收到哪）把跨场景的因果收束显式化，这是普通摘要最容易丢失的结构。

## 8. 小说与剧本的切分逻辑

两种输入共用同一套输出 schema，但切分方式不同。

### 8.1 小说

小说是非结构化文本，最难的环节是切分。确定性脚本只做可靠的结构切分：

1. **章节标题**：识别 `第X章`、`第X回`、`Chapter X`、`序章/楔子/尾声/番外` 等。
2. **空行分块**：空行分隔的连续段落块作为候选场景。
3. **语义边界**：地点切换、时间跳转、视角切换，交给 LLM 在生成场景卡时决定是否合并或细分。

不拆分的边界：

- 自由间接引语与内心独白留在原场景内。
- 连续对话块不因"一句一空行"而拆散。

### 8.2 剧本

剧本是半结构化文本，切分相对确定：按场景标题（SLUGLINE）切分，从一条场景标题到下一场景标题前为一个场景。识别 `INT.` / `EXT.` / `INT./EXT.` / `内景` / `外景` / `第X场` 等。场景内保留动作描写、对白的角色归属、转场标记。

## 9. 七步工作流

1. **读入**：检测编码并转换，归一化换行（统一 LF），按口径统计字数。
2. **档位判定**：空文档或超 15 万字则声明不予处理并停止；< 1000 字按精读档。
3. **格式识别**：自动判断小说还是剧本。
4. **确定性切分**：按模式切分场景与段落，分配稳定 ID。
5. **LLM 提炼**：维护 canonical 名 + 别名表，逐场景生成场景卡，并生成总览、结构图、人物索引、伏笔回收表。
6. **组装**：按输出骨架与档位裁剪原文，写成单文件 Markdown。
7. **校验**：逐项校验，全部通过才算完成。

## 10. 校验机制

校验判据（全部满足才通过）：

- 场景 ID 唯一，且与切分结果一一对应。
- 每个锚点的位置（段落号，或场号 + 行偏移）在原文范围内存在。
- `因果` 引用的场景 ID 存在（允许标注"无"的空侧）。
- 人物卡、伏笔表引用的章节 / 场景 ID 存在，无孤儿引用。
- 字数硬上限合规。

这些判据不是可有可无的检查，而是保证"地图"和"原文"之间不会断链：ID 唯一保证可寻址，锚点存在保证可定位，引用存在保证可回溯。

## 11. 三个脚本的分工

- `scripts/prep.py <输入>`：编码检测、换行归一、字数统计、档位判定、模式识别；输出 `*.normalized.txt` 与 `*.prep.json`。
- `scripts/split.py <规范化文本> --mode <novel|screenplay|auto>`：确定性切分，输出 `*.split.json`（含章节、段落、候选场景与 ID）。
- `scripts/validate.py <输出md> <切分json>`：校验场景 ID、锚点、引用与字数，输出 JSON 报告，硬性错误返回退出码 1。

脚本全部用 Python 标准库，不依赖第三方包。

## 12. 设计取舍与边界

- **单文件 vs 目录**：选单文件，避免目录臃肿，代价是超长文本必须靠分档降级。
- **段落号 vs 行号**：选段落号，抗换行格式变化；剧本例外，用场号 + 行偏移。
- **局部稳定 ID**：用"章内序号"而非全局递增，降低原文修改后的漂移。
- **只支持文本**：PDF / EPUB / DOCX / Final Draft 等格式暂不处理。
- **拒绝上限**：超过 15 万字直接拒绝，不提供拆分建议。

## 13. 一次完整走查

以 `examples/sample-novel.txt` 为例：

1. `prep.py` 识别为 UTF-8，字数 72，档位 `full`，模式 `novel`。
2. `split.py` 识别出两章，6 个段落，6 个候选场景，ID 为 `s01-01` 到 `s02-03`。
3. LLM 为每个候选场景填场景卡（本样例每个空行块恰好是一段，实际长篇中会合并多个段落为一个场景）。
4. 组装成单文件，`validate.py` 返回 0 错误。

完整示例输出见 `examples/sample-novel.output.md`。
