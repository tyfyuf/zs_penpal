## 二、主要问题汇总

### P1：摘要 Worker 初始化失败可能阻止主窗口启动

涉及：

- `src/main/index.ts`
- `src/main/services/summary-job-manager.ts`
- `src/main/services/doc-summary-maintenance.service.ts`

当前启动流程在创建主窗口前等待摘要 Worker 和摘要维护初始化。如果 Worker 启动、工作区读取或维护初始化失败，可能导致 `app.whenReady()` 异步流程拒绝，从而出现主窗口不创建、IPC 未注册或应用启动后不可用的问题。

建议：先注册基础 IPC 并创建主窗口，再异步初始化摘要 Worker 与维护服务；摘要系统故障不应阻止应用进入主界面。

### P1：摘要 Worker `error`/`fatal` 异常收尾不完整

涉及：

- `src/main/services/summary-job-manager.ts`
- `src/main/services/summary-worker.ts`

Worker 发生 `error` 或 `fatal` 时，当前没有始终完成 Worker 引用清理、ready 状态清理、活动任务拒绝、异常 Worker 终止和可靠重启。失效 Worker 可能被后续任务继续使用，任务也可能长期等待。

### P1/P2：Worker 自动重启策略过于有限

当前整个应用生命周期最多自动重启一次，且：

- 没有退避机制；
- Worker 稳定运行后不会重置失败次数；
- 连续崩溃后没有明确不可用状态；
- 新任务可能卡住，而不是立即返回明确错误。

建议采用有限次数、带退避的重启，并在超过上限后暴露明确的摘要服务不可用状态。

### P1/P2：Worker fatal 后可能破坏同一对象的串行保护

涉及：

- `src/main/services/summary-job-manager.ts`

`rejectAll()` 会清理 `active` 和 `activeByKey`，但此前创建的链式 Promise 仍可能继续执行。Worker 重启后可能出现同一文档、资源、对话或大摘要任务并发写入，或新请求绕过旧链式任务。

### P1/P2：摘要任务取消协议没有真正贯通

涉及：

- `src/shared/summary-job-protocol.ts`
- `src/main/services/summary-worker.ts`
- `src/main/services/summary-job-manager.ts`

Worker 创建了 `AbortController` 并处理了取消消息，但信号未传递到具体摘要服务；IPC 也没有摘要任务取消入口，Renderer 没有取消按钮。

如果产品不要求用户取消摘要，可将其定义为协议冗余并降级；如果需要取消，则属于实际功能缺陷。

### P1/P2：应用退出流程存在后台任务竞态

涉及：

- `src/main/index.ts`
- `src/main/services/summary-job-manager.ts`
- `src/main/services/doc-summary-maintenance.service.ts`
- `src/main/services/vector.service.ts`

当前大致顺序为：Renderer flush → Git 提交 → 关闭摘要维护 → 关闭摘要 Worker。主要风险：

- Git 提交时摘要 Worker 仍可能写文件；
- 摘要维护在提交前仍可能排队任务；
- 向量任务没有统一等待或取消；
- shutdown 只等待 `active.size`，没有覆盖队列、链式 Promise 和维护队列；
- 超时 kill 后任务状态没有统一收尾。

建议先停止新任务，再处理摘要、向量任务，最后执行 Git 提交和应用退出。

### P2：重复触发 `before-quit` 存在退出竞态

涉及：

- `src/main/index.ts`

第二次触发退出事件时可能直接返回，不再调用 `preventDefault()`，存在绕过异步退出收尾流程的风险。

### P2：对话摘要退出重试逻辑未接入

涉及：

- `src/main/ipc/index.ts`

`onBeforeQuitTasks()` 中存在 `retryPendingSummariesInWorker()` 调用，但项目内未发现实际调用方。该逻辑当前实际上没有生效，需要决定接入退出流程、改为启动时恢复，或删除。

### P2：摘要维护关闭时不会等待当前维护队列

涉及：

- `src/main/services/doc-summary-maintenance.service.ts`

`shutdownDocSummaryMaintenance()` 只清理 timer 和重试状态，不会等待已经进入 `maintenanceQueue` 的任务，也不会取消正在执行的摘要任务。这可能导致退出、迁移或 Git 提交时仍有摘要写入。

### P1/P2：工作区迁移没有协调未保存内容与后台任务

涉及：

- `src/main/ipc/index.ts`
- `src/main/services/migration.service.ts`

`workspace:migrate` 当前没有统一执行：

- 请求主 Renderer flush；
- 等待编辑器内容落盘；
- 暂停摘要维护；
- 等待或暂停向量任务；
- 阻止迁移期间新的文件写入。

可能导致迁移复制旧内容，或摘要、向量索引继续写入旧工作区。

### P1/P2：IPC 缺少运行时参数与来源窗口校验

涉及：

- `src/main/ipc/index.ts`
- `src/preload/index.ts`
- `src/shared/ipc.ts`

当前主要依赖 TypeScript 类型，运行时缺少：

- 请求结构校验；
- 字符串长度和上传大小限制；
- 枚举和数字范围校验；
- 来源窗口校验；
- 高风险操作的额外边界检查。

重点风险入口包括删除、永久删除、工作区迁移、Git 回滚、API 配置、文件导入和向量索引操作。

### P1/P2：实体 ID 与路径缺少统一安全边界

涉及：

- `src/main/services/file.service.ts`
- 多个 IPC handler

大量 `projectId`、`docId`、`chatId`、`resourceId` 直接参与路径拼接，尚未看到统一的：

- ID 格式校验；
- 项目存在性校验；
- 对象归属校验；
- 状态校验；
- 路径必须位于工作区根目录内校验。

需要进一步确认读取、重命名、删除和恢复入口是否可能跨项目、访问回收站内容或操作非正常对象。

### P2：Preload 暴露泛化 `send`

涉及：

- `src/preload/index.ts`
- `src/preload/index.d.ts`

当前暴露 `send(channel, payload)`，而实际主要用途是 `app:flushed`。建议改为专用方法或至少实施 channel 白名单。

### P2：`app:flushed` 握手缺少 requestId 与发送方校验

涉及：

- `src/main/index.ts`
- `src/renderer/src/App.tsx`
- `src/preload/index.ts`

当前通过 `ipcMain.once('app:flushed')` 等待 Renderer flush，没有 requestId/token，也未校验发送方是否为主窗口。迟到事件或设置窗口事件理论上可能误完成一次 flush。

### P2：多窗口广播没有区分目标语义

涉及：

- `src/main/window.ts`

当前 `broadcast()` 同时向主窗口和设置窗口发送所有事件，可能造成流式对话、摘要进度、迁移事件等在不相关窗口中产生串扰。

建议区分主窗口专属、设置窗口专属和全局同步事件。

### P2：第二实例与外部文件传递存在时序和覆盖风险

涉及：

- `src/main/index.ts`

当前只保存一个 `pendingExternalFile`，存在：

- 主窗口建立前事件丢失；
- 多个外部文件只处理第一个；
- 多次事件互相覆盖；
- 主窗口尚未完成加载时无法可靠投递。

建议改为路径队列，待主窗口加载完成后统一消费。

### P2：向量任务没有统一退出收尾

涉及：

- `src/main/services/vector.service.ts`

向量操作虽然按项目串行，但退出时没有统一等待、取消、超时和恢复机制。当前索引任务可能被强制终止，Git 提交可能遗漏最新索引状态。

### P2：普通对话、摘要和向量任务没有供应商级并发协调

涉及：

- `src/main/services/api.service.ts`
- `src/main/services/summary-job-manager.ts`
- `src/main/services/summary-task-scheduler.ts`
- `src/main/services/vector.service.ts`

三类任务各自运行，没有共享供应商级的并发限制、限速、重试退避、优先级和请求队列。后台摘要任务可能与普通对话共同冲击同一个 API，造成延迟、限速或失败。

### 编码与用户可见文本存在乱码风险

## 三、当前总体判断

目前系统的主要风险并非核心功能全部失效，而是集中在：

1. 后台 Worker 异常和退出时状态收尾不完整；
2. 摘要、向量、Git、迁移之间缺少统一协调；
3. IPC 缺少运行时安全边界；
4. 多窗口与外部文件事件缺少明确的目标和队列语义；
5. 普通对话与后台任务没有供应商级并发控制；
6. 项目中仍有用户可见乱码和构建元数据乱码风险。

### 2A-01｜P1：项目/实体归属与状态校验不集中，存在越过生命周期边界的入口

涉及：

- `src/main/services/file.service.ts`
- `src/main/ipc/index.ts`

确认到的行为：

1. `assertProjectContentMutable()` 只检查系统项目保护，没有统一拒绝“项目不存在”“项目已在回收站”“项目状态异常”。因此 `createDoc()`、`createChat()`、资源创建/上传等调用链在缺少严格上层约束时，可能向不存在或已删除的项目目录写入孤儿数据。
2. `findDocMeta()` 与 `getChatMeta()` 遍历 `listProjects()` 的全部项目，包含回收站项目；按 ID 读取时没有把“正常/归档/回收站”作为统一前置条件。
3. `readDoc()`、`getChat()`、资源读取等路径主要依赖拼接后的路径和元数据文件是否存在，没有统一验证元数据中的 `id`、`projectId` 与请求参数一致。
4. `purgeProject()`、`purgeDoc()`、`purgeChat()` 没有在服务层强制要求对象已经处于回收站/归档状态；`restore*()` 也没有统一拒绝对已经正常的对象重复执行。

影响：

- 错误的 `projectId + entityId` 组合可能读取或操作错误对象；
- 回收站内容可能通过内部调用链继续被读取、修改或写入；
- 永久删除入口缺少服务层状态闸门，未来任何新的 UI/IPC 调用都可能绕过“先移入回收站、再永久删除”的产品语义；
- 异常元数据可能被构建进工作区快照，形成跨项目引用或孤儿文件。

建议：建立统一的 `assertProjectExists/Normal`、`assertEntityBelongsToProject`、`assertEntityState`、`assertSafeWorkspacePath`，所有文件与派生数据读写/删除入口都经过同一组校验；将“删除、恢复、永久删除”状态转换表在服务层强制执行，而不是依赖 Renderer 约束。

### 2A-02｜P1/P2：创建、删除与索引更新不是事务，失败时可能留下半成品或索引悬挂

涉及：

- `src/main/services/file.service.ts`
- `src/main/services/migration.service.ts`

确认到的写入顺序包括：

- 创建项目：先更新 `app-index.json`，再创建项目目录和 `meta.json`；
- 创建文档/对话：先写元数据，再写正文/JSONL；
- 创建资源：依次写入 `source.bin`、`content`、`meta.json`；
- 永久删除项目：先从索引移除，再递归删除目录；
- 永久删除文档/对话：多个正文、元数据、摘要、快照文件分步删除；
- 工作区迁移：目录替换完成后才写入新的工作目录配置。

任一步骤失败，都可能出现“索引存在但目录不存在”“目录存在但索引不存在”“元数据存在但正文缺失”“源文件与规范化正文只有一部分写入”等中间状态。当前没有统一事务日志、提交标记、启动时修复或完整性扫描机制。

建议：对多文件实体使用 staging 目录 + 原子 rename；对索引和实体变更增加事务/恢复标记；启动时执行孤儿目录、孤儿元数据、缺失正文和派生文件引用扫描，并把修复结果明确告知用户。永久删除应先完成物理操作并记录可恢复的删除事务，或采用可重入的两阶段删除协议。

### 2A-03｜P1：工作区迁移会误处理“目标路径是文件”的情况，存在删除用户文件的风险

涉及：

- `src/main/services/migration.service.ts:75-84`
- `src/main/services/migration.service.ts:18-39`

迁移前校验只在目标存在且为目录时检查目录是否为空；如果目标路径存在但本身是普通文件，校验会直接放行。随后 `renameDirAtomically()` 将任意已存在目标都视为“空目录”并执行递归删除，再把 staging 目录改名为该路径。

影响：迁移到一个已有文件路径时，目标文件可能被删除。该问题不是普通失败，而是高风险的破坏性边界条件。

建议：目标存在且不是目录时立即拒绝；目标目录还应使用 `lstat/realpath` 检查符号链接；删除目标前再次确认它仍是同一个、确实为空的目录，避免检查与删除之间的 TOCTOU 风险。

### 2A-04｜P1/P2：删除、永久删除与后台摘要/向量任务没有统一协调

涉及：

- `src/main/ipc/index.ts`
- `src/main/services/file.service.ts`
- `src/main/services/summary-job-manager.ts`
- `src/main/services/doc-summary-maintenance.service.ts`
- `src/main/services/vector.service.ts`
- `src/main/services/summary.service.ts`

确认到的联动缺口：

- 删除项目时 IPC 取消了文档摘要维护，但没有看到同等级别的“取消/等待该项目全部向量任务、资源蒸馏和摘要任务”的统一协议；
- 永久删除项目直接递归删除目录，后台任务仍可能持有旧项目 ID 并在删除后尝试写派生文件；
- 永久删除文档会删除文档正文、元数据和文档摘要，但大摘要（rollup）中的成员列表需要后续重建/清理，向量索引删除依赖 IPC 之后异步排队；
- 删除资源会同步删除资源摘要/checkpoint，但向量删除仍是异步排队，且没有统一等待任务完成的生命周期屏障；
- 恢复文档/项目后，没有在恢复入口建立“派生摘要/rollup/向量索引状态重新评估并排队修复”的统一动作。

影响：可能出现派生数据引用已删除对象、删除后旧任务重新写回已删除对象、恢复后摘要/索引长期缺失或过期。单项队列不能替代实体删除与所有派生任务之间的项目级屏障。

建议：以项目为边界建立统一的 quiesce/cancel/drain 生命周期协议；删除前阻止新任务、等待或取消现有任务、再改变实体状态；永久删除前确认没有任务引用该项目；删除/恢复后统一重建 rollup、摘要状态和向量索引状态，并使所有异步任务写入前再次验证实体版本/状态。

### 2A-05｜P1/P2：工作区迁移期间没有冻结编辑与派生任务，配置切换也可能与物理目录脱节

涉及：

- `src/main/services/migration.service.ts`
- `src/main/ipc/index.ts`
- `src/main/services/doc-summary-maintenance.service.ts`
- `src/main/services/vector.service.ts`

迁移流程在复制源目录前没有要求 Renderer flush、没有暂停编辑写入、没有暂停摘要维护或向量任务，也没有阻止迁移期间新任务进入。复制过程中源文件发生变化时，目标可能只是一个不一致快照。物理目录替换成功后，`setConfig()` 若失败，函数会进入失败分支，但目标目录已经生效，配置仍可能指向旧工作区。

此外，迁移完成后旧目录保留，迁移开始前已经捕获旧路径的后台任务可能继续写入旧目录。当前进度百分比是阶段常量，并不能证明真实复制进度或后台任务已静止。

建议：迁移前进入 workspace-wide quiesce 状态，flush 并等待所有文件写入、摘要、资源蒸馏、rollup、向量任务结束或安全取消；复制期间拒绝新写入；配置切换采用可回滚事务，并在切换后重新加载/校验工作区；迁移后再释放任务闸门。

### 2A-06｜P2：功能指引项目初始化/同步/重建不是事务，异常中断可能留下不完整系统项目

涉及：

- `src/main/services/file.service.ts`
- `src/main/services/feature-guide-content.ts`

`ensureFeatureGuideProject()` 会依次创建项目、文档、正文、元数据和指引对话，最后才设置 `featureGuideInitialized`。中途失败时可能留下部分项目和部分文档。`force=true` 重建时会先从索引移除旧项目并递归删除目录，再开始创建新项目；如果后续创建失败，用户会得到一个被删除但未重建完成的状态。

`syncFeatureGuideProject()` 会在启动/配置变化时重写所有内置文档，并删除旧版本中多余文档。这符合“系统文档不可由用户编辑”的保护方向，但目前缺少版本同步事务与失败恢复，且不完整项目的“已存在”状态与“已初始化”标记之间没有完整性校验。

建议：使用临时系统项目完成全量创建与校验后再一次性替换；保留旧版本直到新版本通过完整性检查；启动时校验固定文档数量、`systemOrder`、内容存在性和指引对话完整性；失败时保留旧项目并给出可恢复错误。

### 2A-07｜P2：资源目录与资源元数据缺少完整性及归属校验

建议：读取和列举时校验目录名、元数据 ID、项目归属和必需文件；把损坏资源标记为不可用并隔离，而不是静默跳过或继续进入摘要/向量流程；保存、删除和外部导入也复用相同校验。

### 2A-09｜P2：恢复后的派生数据修复策略不明确，可能长期依赖“下次使用时再生成”

涉及：

## 八、阶段 2A 结论

阶段 2A 的核心结论是：文件格式转换和同名资源导入已有可用基础，当前最需要优先修复的不是摘要提示词，而是“实体生命周期 + 派生任务生命周期”之间没有统一的服务层边界。

建议后续修复顺序：

1. 先修复工作区迁移目标为普通文件的破坏性问题，并建立路径/实体归属/状态校验；
2. 建立删除、永久删除、恢复前后的项目级任务屏障；
3. 为创建、删除、指引项目重建和迁移补上可恢复事务；
4. 建立源实体变更到摘要、rollup、向量索引的统一 dirty/repair 调度；
5. 增加生命周期和文件格式回归测试；
6. 最后再根据测试结果细化资源转换与一致性提示的 UI。

上述项目均为审计结论，尚未实施修复，等待后续阶段批准。

## 阶段 2C-2：资源派生链路交叉竞态验证

### 2C-2-01｜P1｜资源编辑保存与重新导入没有互斥屏障

涉及：

- `src/renderer/src/components/ResourceViewer.tsx`
- `src/main/ipc/index.ts`
- `src/main/services/file.service.ts`

`ResourceViewer` 内部使用 `savePromise` 串行化连续保存请求，但“重新导入”操作没有等待当前保存完成，也没有在 `saving` 状态下禁用。按钮目前只检查 `repairing` 和 `distilling`，因此用户可以在 `resource:saveText` 尚未完成时发起 `resource:replace`。

可能时序如下：

1. 编辑器当前内容为 A，用户点击保存，开始写入 A；
2. 保存请求尚未完成时，用户选择重新导入内容 B；
3. `resource:replace` 与旧的 `resource:saveText` 的完成顺序不受 Renderer 控制；
4. 如果旧保存在重新导入之后完成，可能把 A 写回并覆盖 B；
5. 随后的 `resource:read`、`lastSavedContentRef`、dirty 状态和摘要刷新事件可能分别对应不同版本。

这不是 `2B-12`“切换标签未 flush”或 `2B-13`“关闭标签保存收尾”的重复问题，而是同一个资源编辑器内两种互斥变更操作的交叉时序缺口。当前为静态确认，尚未进行人工竞态复现。

建议：重新导入、手动保存、关闭/切换前 flush 统一进入同一个资源编辑操作队列；重新导入开始前等待保存完成，或明确取消/丢弃待保存版本；完成后以服务端返回的版本/指纹刷新编辑器和 dirty 状态。

### 2C-2-02｜P1/P2｜资源变更入口没有共享的资源级互斥队列

涉及：

- `src/main/services/file.service.ts`
- `src/main/services/resource-conversion.service.ts`
- `src/main/ipc/index.ts`

当前 `resourceCreateLocks` 只保护新建资源及其同名处理。`saveResourceText`、`replaceResourceBytes`、外部文件导入的 `overwrite` 分支和 `deleteResource` 没有复用同一个资源级或项目级变更队列。`assertResourceMutationAllowed` 只检查摘要是否正在生成，不承担互斥作用；`atomicWrite` 也只保证单个文件的写入方式，不保证一次资源变更涉及的多个文件作为一个操作顺序完成。

因此，即使 Renderer 后续补上按钮禁用，其他窗口或直接并发的 IPC 请求仍可能交叉修改同一个资源。尤其是以下操作组合存在覆盖或不一致风险：

- 保存正文与重导入；
- 保存正文与 overwrite 导入；
- 保存/重导入与删除；
- 删除与随后到达的旧写请求。

这条记录与 `2A-02` 的“多文件变更失败时缺少事务”不同：`2A-02`关注单次操作中途失败留下半成品，本条关注多个合法变更操作之间没有统一顺序，导致后完成的旧操作覆盖新操作或重新创建已删除资源。它也与 `2A-04` 的“删除与后台摘要/向量任务缺少生命周期协调”不同，本条覆盖普通资源变更入口之间的互斥缺失。

建议：以资源 ID（必要时以项目 ID）建立统一变更队列，覆盖保存、重导入、overwrite、删除及其元数据/正文/源文件更新；每次变更携带版本或源指纹，并在提交前再次确认目标实体仍存在且版本未被替换。

### 2C-2 已确认的既有问题与交叉表现

### 2C-3-01｜P2｜发送前置失败会先持久化用户消息，但没有可恢复的重试状态

- **涉及文件**：`D:\ds h-project\src\main\services\api.service.ts`、`D:\ds h-project\src\main\ipc\index.ts`、`D:\ds h-project\src\renderer\src\components\chat\ChatPane.tsx`

### 2C-3 对既有问题的闭环确认（不新增重复编号）

#### 1. `2B-03`：普通消息重复注入已由静态路径确认

普通发送会先将当前用户消息追加进 JSONL，然后重新读取聊天历史。`buildMessages()` 会把该消息包含在 `historyMsgs` 中，同时由于 `appendUser = true`，又把 `req.userText` 和当前附件放入 `tailMsgs`。`applyBudget()` 的返回结构会同时保留历史消息和尾部消息；在预算足够时，当前用户消息确实会在最终请求中出现两次，而不是仅仅“可能重复”。

这会增加提示词 token，并可能使模型把同一问题误判为连续两次用户意图。该确认更新 `2B-03` 的性质与依据，不建立新编号。

#### 2. `2B-26`：连续追问和重生成中的历史附件正文生命周期已确认存在语义风险

当前 `lastUserAttachments()` 与 `lastUserDocAttachments()` 从历史中只取最近一条带附件的用户消息。因而：

- 后续用户消息没有附件时，系统仍可能把最近一次旧附件正文作为本次请求的附件正文注入；
- 更早的附件不会继续以正文形式注入，只保留其消息级身份信息（如果对应用户消息仍在历史中）；
- 重生成模式不携带明确的目标用户消息 ID 或目标附件 ID，而是通过“历史中最近一条带附件的消息”恢复附件。若目标回答对应的用户消息没有附件、但更早消息有附件，重生成可能错误恢复这份更早的附件；
- Renderer 在重生成时会创建新的 `userMessageId`，但不会新增用户消息，因此这个 ID 不能承担“被重生成回答所对应的用户消息”这一绑定职责。

附件消息身份提示已经能够让模型知道名称、类型、身份 ID 和消息来源，但它不能弥补正文选择范围错误。该问题仍需产品层明确“附件正文只在上传当轮有效”还是“附件在本对话内持续可引用”；本阶段确认当前实现至少存在“最近附件复用/重生成错配”的闭环风险，归入既有 `2B-26`。

#### 3. `2B-02`：重生成目标查找与追加写交叉风险属于既有 JSONL 写入问题的运行时表现

重生成时，主进程删除逻辑上的最后一条 assistant，并在成功后通过 `replaceLastAssistantMessage()` 再次扫描 JSONL、替换当前最新 assistant。该操作没有显式传入需要替换的 assistant message ID。正常单请求、单窗口使用时通常指向最后一条回答；但在追加消息、另一个重生成请求或退出 flush 交叉到达时，扫描到的“最新 assistant”可能已不是最初想重生成的目标。

这不是新的独立数据模型根因：它依赖于追加和整体重写没有进入同一个聊天写入队列，属于 `2B-02` 已记录问题的具体表现。本阶段仅补充“重生成目标可能随并发写入漂移”的影响范围。

#### 4. `2B-04`、`2B-05`、`2B-06`、`2B-24`、`2B-25`：取消、关闭和旧事件组合未发现新的根因

静态闭环检查确认以下行为仍与 2B 结论一致：

- Worker/摘要任务取消和应用退出收尾仍由 2B-24、2B-25 覆盖。

### 3A-1-01｜P2｜API 连接测试没有验证所选协议和实际模型生成能力

- **涉及文件**：
  - `D:\ds h-project\src\main\services\api.service.ts`

- **依据**：`testConnection()` 和 `listModels()` 都通过 `createOpenAIClient(...).models.list()` 进行测试；它们没有读取 `settings.apiProtocol` 来选择 Chat Completions 或 Responses，也没有用当前 `settings.model` 发起最小生成请求。

### 3A-1-02｜P1/P2｜Responses 普通对话对所有供应商强制发送 `reasoning.summary: auto`

- **涉及文件**：`D:\ds h-project\src\main\services\llm\llm-client.ts`
- **依据**：`responseRequestFromChatBody()` 对没有私有结构化推理控制字段的普通请求默认组装 `reasoning: { summary: 'auto' }`，随后所有 Responses 请求都会携带该字段，除非走到特定的错误重试分支。
- **可观察场景**：某个 Responses 兼容网关只兼容基础 `model/input/stream`，不识别 OpenAI 的 reasoning summary 扩展；或者模型支持思考但不支持该 summary 参数。请求可能直接 400，或因供应商启用/生成推理摘要而增加延迟与输出成本。
- **根因**：将“希望显示推理摘要”和“Responses 供应商默认行为”绑定在同一请求构造路径，并对未知兼容网关使用了主动扩展字段。
- **影响**：普通对话可能出现协议拒绝、速度下降或额外 token 消耗；这与此前用户观察到部分模型延迟较高的风险方向一致，但本次未进行真实 API 验证。
- **建议**：未知供应商默认不发送 reasoning 扩展；只有能力档案明确支持且用户/系统需要时才发送。保留针对明确错误的运行时学习，但应把 HTTP 异常和响应体 `status: failed` 两类失败统一纳入兼容降级设计。
- **去重说明**：本条只记录“请求构造过度发送字段”的根因；reasoning 事件解析、思维链回放和工具循环留给 3A-2，不在此重复编号。

### 3A-1-03｜P2｜Responses 的 reasoning 兼容降级只覆盖抛出异常，不覆盖成功 HTTP 返回的失败状态

- **涉及文件**：`D:\ds h-project\src\main\services\llm\llm-client.ts`
- **依据**：`ResponsesAdapter.createChatCompletion()` 只在 `responses.create()` 抛出且错误文本符合 `isUnsupportedReasoningSummaryError()` 时，才重试不带 reasoning summary 的请求。若服务商以 HTTP 200 返回 `status: 'failed'` 和 `error.message`，代码是在请求返回后才检查失败并直接抛错，不会进入同一降级分支。
- **可观察场景**：兼容层不使用 HTTP 4xx 表示参数不支持，而是返回结构化失败对象时，第一次请求失败后不会自动尝试去掉 reasoning summary。
- **根因**：兼容回退逻辑分散在 transport catch 中，未抽象为“统一识别请求拒绝并重建请求”的流程。
- **影响**：同一个供应商在不同错误传输方式下表现不一致；本可降级成功的普通 Responses 对话直接失败。
- **建议**：统一处理 HTTP 异常和 Responses 返回体中的失败状态；只有错误明确指向 reasoning summary 不支持时才降级，避免把业务失败误判为协议失败。
- **去重说明**：本条是失败承载形式处理不一致；与 3A-1-02 的字段过度发送是两个根因，3A-2 只继续审计 reasoning 内容解析与回放，不重复该请求回退问题。

### 3A-2-01｜P1/P2｜非正常终止和提前结束的流被当作正常回答

- **涉及位置**：
  - `D:\ds h-project\src\main\services\llm\llm-client.ts` 的 `responseStreamToChatStream()`；
  - `D:\ds h-project\src\main\services\api.service.ts` 的 `streamAnswerWithTools()`。
- **依据**：Chat 流式循环只记录 `choice.finish_reason`，Responses 适配器将 `response.incomplete` 转换为 `length` 或 `stop`。但 `streamAnswerWithTools()` 在普通回答路径仅检查 `state.content` 和 `state.reasoning` 是否为空，随后直接返回成功，没有根据 `finish_reason` 判断 `length`、`content_filter` 等非正常收尾，也没有要求 Responses 流必须出现 `response.completed` 或 `response.incomplete` 终止事件。
- **影响**：
  - Chat 的 `finish_reason: length` 可能被当作完整回答持久化；
  - Responses 的 `incomplete_details.reason: content_filter` 被映射为 `stop`，用户看不到“回答被截断/过滤”的明确提示；
  - 兼容网关在传输中提前结束但已经返回部分文字时，部分回答可能被当作成功结果保存；
  - 长回答或网络/网关异常时，用户容易误以为内容完整。
- **性质**：这是流式收尾语义缺失的新根因，不是 `2B-04` 的旧事件 requestId 校验问题，也不是 `3A-1-03` 的非流式 Responses `status: failed` 回退问题。

### 3A-2-02｜P1/P2｜统一的增量片段合并启发式可能吞掉合法重复文本

- **涉及位置**：`D:\ds h-project\src\main\services\api.service.ts` 的 `mergeStreamFragment()`。
- **依据**：函数在不知道供应商片段是“增量”还是“累计全文”的情况下，先使用 `incoming === previous`、`previous.endsWith(incoming)`、`incoming.startsWith(previous)` 以及最长重叠匹配进行去重。该函数同时用于回答正文、思维过程和工具参数。
- **可观察场景**：若真实的下一个增量片段恰好等于当前文本的尾部，`previous.endsWith(incoming)` 会将它判断为重复并丢弃。例如前一片段结尾和下一片段都为相同词语时，回答会少字；工具参数被吞掉后还可能变成非法 JSON。最长重叠匹配也无法区分“供应商重发”与“正文合法重复”。
- **影响**：正文/思维过程内容缺字，工具参数偶发解析失败，随后误触发工具修复或无工具降级；不同模型的输出结果可能出现难以复现的差异。
- **性质**：这是片段合并策略本身的歧义，不与摘要输出上限或 `3A-2-01` 的终止状态混同。
- **建议**：按适配器记录供应商的片段语义，增量模式默认追加，累计模式按明确的累计游标替换；不要用通用字符串重叠猜测协议语义。工具参数应使用独立的增量累积器，并加入重复/缺片离线测试。

### 3A-2-03｜P1/P2｜Responses 的最终 `.done` 内容在已有 delta 后被无条件忽略

- **涉及位置**：`D:\ds h-project\src\main\services\llm\llm-client.ts` 的 `responseStreamToChatStream()`。
- **依据**：适配器使用 `textPartsWithDelta`、`reasoningPartsWithDelta` 和 `toolArgumentsWithDelta` 记录某一内容分片是否出现过 delta。一旦集合中存在对应键，就跳过 `response.output_text.done`、reasoning `.done` 或 `response.function_call_arguments.done` 的最终全文/完整参数。
- **影响**：如果中途缺少一个 delta、兼容网关只发送了部分 delta，或网关在 `.done` 中提供了更完整的累计值，适配器仍然拒绝最终值，结果会留下截断正文、截断思维过程或不完整工具 JSON。工具 JSON 不完整时会被误判为模型工具调用格式错误并进入修复/降级路径。
- **性质**：这是“最终事件被去重保护遮蔽”的独立根因；不能仅归入 `3A-2-02`，因为即使片段合并完全正确，只要 delta 序列不完整，当前 `.done` 策略仍会丢失可用的最终值。
- **建议**：对正文、reasoning 和工具参数分别保存增量值与最终值；`.done` 应作为该分片的权威快照，或至少在最终值更长/不一致时校正累计值。需要同时防止真实重复，而不是简单地因出现过任意 delta 就拒绝 `.done`。

### 3A-2-04｜P2（兼容风险）｜reasoning 字段别名和 Responses reasoning 形状覆盖不完整

- **涉及位置**：
  - `D:\ds h-project\src\main\services\api.service.ts` 的 Chat chunk 处理；

### 3A-2-06｜P2/P3｜原生工具调用被识别前，可能向前端泄漏不会持久化的前置文本

### 3D 已确认的兼容边界

1. **Chat 与 Responses 不是同一 wire format**：当前 Responses 适配器明确重建 `model`、`input`、`stream`、输出 token、`temperature`、`text.format`、工具和工具选择；未列入映射表的 Chat 字段不会自动转发。这一点与 `3A-1-05` 一致，不另立重复问题。
2. **结构化请求的 reasoning 控制与普通聊天不同**：结构化请求通过私有字段进入 adapter，Responses 使用 `effort: none`，Chat 使用已知供应商字段；普通聊天不使用该私有字段。该设计避免把内部控制字段直接发送到 wire，但未知供应商的思维模式方言不能靠静态推断保证。
3. **降级是有界的**：`executeStructuredTask()` 的默认候选路径最多经过主模式、prompt-only 和 compact；能力错误会插入有限次运行时 fallback，`maxAttempts` 还会进一步限制尝试次数。当前未发现由结构化生成重试逻辑本身造成的无限循环。
4. **Responses 的 reasoning summary 与结构化 reasoning control 已分开**：普通 Responses 请求可能请求可见 summary；带结构化控制字段的请求走 provider-neutral reasoning control，不主动请求 summary。这个分支设计本身存在，但普通请求对未知网关过度发送 summary 的问题仍由 `3A-1-02` 负责。
5. **功能指引对话的检索隔离不是协议能力矩阵问题**：主聊天路径已经关闭自动原文检索、项目检索工具和项目资源附件；底层搜索防线不足已归入 `3C-02`，本阶段不重复编号。

### 3D 必须人工执行的最小 API 矩阵

本阶段不调用真实 API。修复前后至少应使用测试 Key 或供应商提供的低成本测试额度，逐项记录 HTTP 状态、请求字段、响应终止状态、是否产生 reasoning、usage 和用户可见结果：

1. Chat Completions：普通模型、思考模型、DeepSeek、Qwen、Kimi、一个未知 OpenAI-compatible 网关。
2. Responses：原生/兼容 Responses 服务各至少一个；分别测试普通文本、结构化 JSON、思考摘要和工具调用。

### 4A-2-2 New findings

#### 4A-2-01 | Editor read failure has no stable UI cleanup (P2)

Evidence: `src/renderer/src/components/editor/EditorPane.tsx:187-235`.

The `doc:read` call is inside an async IIFE without `try/catch/finally`. If IPC read fails, the component can produce an unhandled Promise rejection, keep `loading` true, and provide no stable error state. The user may see an endless loading or blank editor.

Recommended fix: add an explicit read-error state and user-facing error message, and guarantee cleanup for read failure, initialization failure, and unmount.

#### 4A-2-02 | Centered-paragraph restoration can select the wrong duplicate paragraph (P2)

Evidence: `src/renderer/src/components/editor/EditorPane.tsx:66-89`.

Persisted formatting stores the old offset and paragraph text. When the old offset no longer matches, `resolveCenteredParagraphs()` searches all identical text with `content.indexOf()` and chooses the nearest offset. If the document contains repeated paragraphs, editing or insertion can move the centered decoration to the wrong occurrence.

Recommended fix: use a stable paragraph identity or strict surrounding-context match instead of only identical text plus nearest offset.

#### 4A-2-03 | file.service contains user-visible mojibake (P1)

Evidence: `src/main/services/file.service.ts:867-940`.

Several strings are already corrupted in source, rather than being TypeScript nullish-coalescing syntax. Affected paths include the resource-distilling read-only message, the external-file empty-content message, the unsupported-extension message, and the external-file read failure message. They contain mojibake strings and can be shown directly to users.

This is related to the earlier general encoding finding, but this entry records the concrete output locations that must be repaired.

#### 4A-2-04 | Legacy feature-guide title migration table contains literal question marks (P2)

Evidence: `src/main/services/file.service.ts:164-180`, `legacyOrderByTitle`.

The migration table contains values consisting of literal question-mark placeholders instead of the old Chinese document titles. New projects and projects with valid `systemOrder` metadata can still work because matching also checks order and current title. Historical guide projects that only have old titles may fail migration, create duplicates, or lose deterministic ordering.

This is independent of the non-transactional synchronization finding `2A-06`: that finding covers interruption safety, while this finding covers corrupted migration identifiers.

#### 4A-2-05 | Document and resource encoding handling is inconsistent (P2)

Evidence:

- `src/main/services/text-decoding.service.ts:78-95` detects replacement characters, NULs, control characters, and mojibake;
- `src/main/services/file.service.ts:384-387` makes `readDoc()` return only decoded text and discards `DecodedText.info`;
- `src/main/services/file.service.ts:796-815` returns resource encoding metadata but still passes suspicious content to the UI;
- `EditorPane.tsx` has no corresponding encoding warning area.

A suspicious resource can at least expose a warning, while a suspicious writing document can be silently displayed and then reused by summaries or chat context. The fix should define one policy for document/resource read: warn, block, or allow with an explicit status. The existing detector should be reused rather than creating a second detector.

#### 4A-2-06 | Resource distillation status has a short editable race window (P2)

Evidence: `src/renderer/src/components/ResourceViewer.tsx:88-120, 122-160`.

The viewer initially creates the editor while `distillingRef.current` is false, then asynchronously asks `summary:listProject` whether this resource is being distilled. Before that IPC call returns, a user can edit, paste, or trigger a save. The editor is switched to read-only only afterward, which violates the product boundary that a resource under distillation must not be editable.

Recommended fix: start conservatively read-only until the initial status is known, or return resource content and distillation status in one consistent backend snapshot.

#### 4A-2-07 | Reimport remains enabled while the initial resource read is pending (P2)

Evidence: `src/renderer/src/components/ResourceViewer.tsx:122-177, 179-217, 253-258`.

The reimport button disables only `repairing` and `distilling`, not `loading`. A user can start `resource:replace` while `resource:read` is still pending. Depending on IPC completion order, the initial read can overwrite recently reimported editor content, metadata, or encoding state.

Recommended fix: disable reimport until the initial read completes and serialize read, save, and reimport per resource, or add a resource version check.

2. Feature-guide documents use `system === 'feature-guide'` read-only mode and hide writing-edit operations.
3. Resource distillation status can switch the editor to read-only through `summary:status`; resource editing is manual-save only.
4. External-file viewer supports temporary editing, filename and source-path display, character count, project search, and upload. Upload uses current editor content and does not overwrite the original external file.
5. DOCX uses Mammoth to HTML and Turndown to normalized text; DOC has normal parsing and a text-only fallback; tables, images, footnotes, and complex formatting have warning or degradation paths.

### 5B-3-01 | P2 | 默认摘要与动态摘要选择在同一请求内重复加载候选

**发现日期**：2026-09-04

**现象/依据**：`buildMessages()` 先后调用 `selectDefaultKeys()` 和 `selectDynamicKeys()`。两者都会调用 `loadCandidates()`；当对话已达到动态学习启动轮数时，同一请求会对同一批 doc/chat/res 候选重新读取并解析。文档候选还可能先读取正文判断短文档，然后再读取文档摘要。

**影响**：项目较大且已进入动态学习的对话每轮会产生额外的磁盘 I/O、JSON 解析和正文读取开销，增加首轮延迟。

**去重判定**：不与 `2B` 摘要生成流程的重复读取合并，也不与 `3B-2-04` 实际注入与记忆卡片不一致合并；本项只记录一次请求内候选加载重复。

**下一步审计方向**：检查是否可在一次 `buildMessages()` 中共享 `Candidate[]` 或按 key 缓存的候选读取结果，同时保持默认与动态选择的优先级和禁用边界。


### 5B-3-02 | P2 | 对话上下文组装中当前文档在一轮请求内重复读取

**发现日期**：2026-09-04

**现象/依据**：`summary-relevance.ts` 的 `buildAnchorEntities()` 为 doc/context 对话读取当前文档；随后 `api.service.ts` 的 `buildMessages()` 又为上下文分片或文档全文读取同一份正文。当前文档需参与候选匹配时，前者还可能是一次独立的全文读取。

**影响**：每轮 doc/context 对话都可能重复读取大文档，增加磁盘 I/O和文本完整性检查开销，并使延迟随文档长度增长。

**去重判定**：与 `2B-2B` 文档摘要生成阶段的重复全文读取不同；本项限定在“对话请求组装”路径。

**下一步审计方向**：检查是否能让候选选择、上下文分片与摘要注入共享本请求的文档内容快照，避免改变原有匹配语义。


### 5B-3-03 | P2 | 激活资源摘要在候选阶段与注入阶段重复读取

**发现日期**：2026-09-04

**现象/依据**：`loadCandidates()` 对所有资源候选先读取资源以检查编码状态，再读取资源摘要；候选选择后，`injectSummaries()` 对每个激活资源重新读取资源检查编码，然后再读取同一份摘要。

**影响**：被激活的资源每轮会至少重复读取一次正文和一次摘要，在资源较多时会放大延迟。

**去重判定**：与 5B-3-01 的“默认/动态两次候选加载”不同；本项记录候选结果已确定后，候选资料与最终注入之间的重复读取。

**下一步审计方向**：检查候选读取结果是否可以随最终激活键传递到注入阶段，同时保留资源编码异常的跳过行为。


### 5B-3-04 | P2 | 摘要候选加载使用无界限 Promise.all 并发读取

**发现日期**：2026-09-04

**现象/依据**：`loadCandidates()` 对 `applicable` 中的所有 key 使用单次 `Promise.all(applicable.map(...))`。没有任务数上限、分批或取消检查。

**影响**：大项目中一次请求可同时触发大量文档、对话和资源文件读取、解析与编码检查，瞬时资源占用和 I/O 并发度可超出正常对话需求。这与后台摘要任务的供应商并发限制是两个层次；本项针对请求内部的文件读取并发。

**下一步审计方向**：检查是否需要限制同时读取数量、在取消或窗口关闭时终止候选加载，并让激活摘要数量限制与资源读取上限一致。
