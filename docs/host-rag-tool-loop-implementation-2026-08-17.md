# 宿主驱动原文检索与有界工具循环实施说明

日期：2026-08-17

## 1. 结论

本轮修复的核心不是继续强化“让模型判断要不要检索”，而是把首次原文检索从模型决策链中移出：每条具有实际信息量的用户问题由 Electron 主进程自动执行一次项目原文混合检索，并把命中的分块作为证据注入本轮请求。模型工具调用只作为追加能力，不能成为检索的唯一入口。

因此，任何 OpenAI-compatible 模型即使不支持 tools，也可以获得宿主检索结果；支持 tools 的模型可以在自动检索不足时用不同查询继续查找，且工具调用次数有上限。

## 2. 原问题根因

此前的 C 层检索由 `planMemory` 先向 LLM 请求一个普通 JSON：

```json
{"needs": [], "vectorQuery": "..."}
```

这不是 OpenAI Function Calling，也没有把 `search_project_source` 工具声明给模型。模型只能输出一段可能正确、也可能为空的 JSON；如果它没有生成 `vectorQuery`，主进程就不会检索。最终回答请求既没有原文片段，也没有工具定义，模型自然可能回答“摘要中没有”或“没有访问原文的权限”。

实机日志 `userData/logs/vector-events-2026-08-17.jsonl` 只有 BGE 加载和索引构建，没有 `stage: search`，说明索引本身已生成，故障发生在检索调用之前，而不是模型文件或索引生成失败。

## 3. 实施内容

### 3.1 宿主自动检索

`src/main/services/api.service.ts` 的 `streamChatInner` 在发送最终回答前执行：

1. 对当前用户问题做轻量低信号判断；问候、感谢等不触发，具体问题默认触发。
2. 调用 `searchVectorIndex(projectId, userText, 5)`。
3. 将命中块以 system message 注入当前请求的连续 system 前缀末尾，使历史仍保持 user/assistant 顺序，兼容更严格的 OpenAI-compatible 服务。
4. 将查询、命中数、失败信息和命中片段写入 `MemoryContext.vectorTrace` / `MemoryContext.vector`。
5. 检索异常只记录为失败并继续请求模型，不阻断聊天。

该路径与 `summaryEnabled`、重新生成模式和 LLM 记忆规划结果解耦。重新生成也会再次检索；关闭摘要后仍可检索。

### 3.2 混合召回

`src/main/services/vector.service.ts` 在原有神经嵌入/特征哈希余弦相似度之外增加轻量字面召回：

- 提取引号内短语、英文/数字专名和中文连续词段；
- 移除“请问、有没有出现、原文中、设定集”等提问脚手架；
- 对原文进行规范化后计算字面命中比例；
- 字面命中与语义分数融合，专名和原文措辞命中优先于模糊语义命中；
- 不引入分词依赖，保留 BGE 优先、特征哈希兜底的现有链路。

当前仍使用 top-k 正分结果，最低相关性阈值和更正规的 BM25/中文分词属于真实语料验收后的调参事项。

### 3.3 有界原生工具循环

当端点接受工具参数时，最终流式请求声明 `search_project_source`：

```json
{
  "query": "短而精确的检索词",
  "topK": 1
}
```

模型可在自动检索结果不足时追加查询。主进程负责解析流式 `tool_calls` 分片、执行本地检索、把结果以 `role: tool` 回传，再请求下一轮回答。单次回答最多执行 2 次工具检索；达到上限后下一轮不再提供工具，模型必须完成回答。

每轮工具检索与自动检索共用同一个“本次记忆”结构，命中块按 `docId:index` 去重，但每一次查询仍保留在 `vectorTrace.attempts` 中。

### 3.4 兼容性降级

工具能力按 `baseURL + model` 在当前进程内缓存。首次请求带 tools：

- 正常接受：记录支持，后续可继续使用；
- 返回 400/404/422 且错误明显涉及 tools、tool_choice、tool_calls、function 或不支持参数：标记不支持，立即重试一次不带 tools；
- 其他错误：按普通聊天错误处理，不伪装成工具不支持。

降级时已经完成的宿主自动检索结果不会丢失，因此不支持 Function Calling 的模型仍能使用原文证据。

## 4. “本次记忆”可观测性

向量部分现在展示：

- 总状态：命中、已检索未命中、检索失败或未触发；
- 每次尝试的来源：自动检索 / 工具检索；
- 每次查询词和命中数；
- 每个命中块的标题、分块编号、相似度、原文预览；
- 自动命中和工具命中的视觉标签及中英文文案。

向量事件日志仍只记录后端、阶段、结果、耗时、块数量等运行元数据，不记录项目 ID、查询、原文或向量。

## 5. 对摘要/蒸馏的影响

摘要和蒸馏链路未被替换：

- 小摘要和大摘要仍按原有设置与结构化生成兼容层运行；
- B 层记忆规划现在只负责选择大摘要，不再负责决定 C 层是否检索；
- 摘要关闭时不再意外关闭原文检索；
- 检索失败不会删除或覆盖摘要，也不会阻断模型回答。

## 6. 本轮验证

已完成：

- `npm run typecheck:node`
- `npm run typecheck:web`
- `git diff --check`
- 工具多调用上限逻辑审查：assistant tool_calls 只包含实际会执行的调用，避免缺少对应 tool response；工具名分片做重复防护。

必须在真实 Electron 运行环境继续验证：

1. 询问只存在于资源区原文、摘要中没有的专名；
2. 检查 `vector-events-YYYY-MM-DD.jsonl` 出现 `stage: search`；
3. 检查“本次记忆”显示自动检索、查询、命中块和原文预览；
4. 检查模型不再声称没有项目原文权限；
5. 在支持工具的模型上要求更换关键词，观察是否出现工具检索；
6. 在不支持工具的兼容端点上确认自动降级且回答仍可使用原文；
7. 关闭摘要后重复测试；
8. 点击重新生成后重复测试。

## 7. 已知限制与后续方向

- 工具能力缓存目前只存在内存，应用重启后会再次探测；
- 混合分数的阈值尚未用真实设定集验收，可能需要抑制低相关性 top-k；
- 当前字面召回是轻量规则，不是 BM25，中文长句和别名召回仍需观察；
- 多个命中块来自同一文件时尚未做完整多样性重排；
- 自动检索注入发生在预算裁剪之后，默认模型上下文足够时没有问题；若用户把上下文上限设得很低，应进一步增加检索片段预算裁剪；
- 索引源指纹和正文修改后的自动增量刷新仍是独立待办；
- 需要用 DeepSeek、OpenAI、Qwen、GLM 等真实兼容端点建立工具能力回归矩阵，并完成低配机器性能验证。
